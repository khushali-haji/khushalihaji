The Problem

Your first read on an international conflict shouldn't take 12 browser tabs

When an international event breaks, a single news report gives you fragments, not holistic understanding. The main location may be named at the top, but the rest of its international dynamics and its actors are never in visual form. You have to look up who is where, and how the geography plays a role, which we know it does. The historical backdrop is assumed to be knowledge the reader already has. And the article's own media slant is invisible unless you already know the outlet's political positioning.

So an engaged reader does the synthesis by hand: open a second map tab to locate where the action occurred, skim Wikipedia to understand the history, and load a media-bias tool to detect the narrative framing. Three tools, ten minutes, and most readers give up before starting. Worse, the most rigorous reporting sits behind paywalls.

How might we take someone from a single article to a geographically-grounded, bias-aware understanding of an event in under a minute?

The mobile interface

Floating overlays on desktop maps are great, but they cover the entire viewport on a mobile screen. Instead of wrapping overlays in tiny scroll zones, I reordered the layout so that the map remains the base layer, and a bottom sheet slides up dynamically.

Key Design Decisions

Decisions and tradeoffs

Four principles came out of the research.

Geography leads, the text supports

Tension: The familiar layout puts the article first and the map off to the side, which leaves the reader doing the spatial work in their head.

Decision: Made the map the primary canvas and anchored every extracted event and actor to coordinates, so the narrative hangs off geography.

↳ Core Principle: Geography is the spine

Progressive rendering over single payload

Tension: Single API payloads are cleaner to maintain, but force a 25-second blank screen.

Decision: Segment the LLM pipeline into four distinct threads, painting the UI sequentially.

↳ Core Principle: Never make them wait

A PDF bypass for scraper paywalls

Tension: Scrapers cannot read premium publications without encountering subscriber login screens.

Decision: Built a PDF upload parser so users can save paywalled pages and process raw text directly.

↳ Core Principle: Meet the reader where the content is

Bias read, labeled as the model's view

Tension: The bias read is itself an automated judgment, and the model can hallucinate or carry its own slant, so presenting it as objective truth would be dishonest.

Decision: Kept the dedicated "Journalistic Analysis" panel, but state plainly in the product that Gemini produced the framing, so readers weigh it as one model's read and not a verdict.

Limitation: A single model grading bias is the current ceiling. A trained or second opinion agent to sort through the framing is the next step (see Reflection).

↳ Core Principle: Make bias visible

AI + Safety Nets

Designing for AI

Language models are probabilistic systems. They can return malformed JSON, hallucinate URLs, or geocode coordinates to the middle of the Atlantic Ocean. Designing for AI requires building defensive UI safety nets around messy data.

Technical Architecture

Under the hood

Conflict Lens is four parts working together.

  • Frontend Framework React with Vite builds the interface, React-Leaflet draws the map over muted greyscale satellite tiles, and the styling is hand tuned in custom CSS.
  • Backend Engine Node and Express run several requests to Google Gemini at once, so each article is broken into structured pieces without a long single wait.
  • Scraper Pipeline Cheerio and Axios pull the text out of a web page, pdf-parse does the same for an uploaded PDF, and a short lived Redis cache remembers recent pages so the same one is never fetched twice.
  • Deployment The interface is served as static files on GitHub Pages, and the data services run on standard cloud servers.

Reflection

What I learned, and what's next

Conflict Lens taught me that designing with AI is really about designing for volatility. We cannot control what the API returns, so the interface has to act as a filter. Keeping the system feeling fast with skeleton loading, setting honest expectations with clear waiting copy, and offering a next step when something fails can turn a fragile AI script into a trustable product.

If I were to expand the scope, I'd bring in a second source for the bias read. Right now the Gemini API handles it alone, and since an AI can hallucinate, a trained agent or an independent check could make that call more reliable. On the interface, I'd build a chronological playback tool that animates the timeline and flies the view to each event pin on the map. I would also add keyboard shortcuts to browse events, and institutional trust scores to help verify citations.
